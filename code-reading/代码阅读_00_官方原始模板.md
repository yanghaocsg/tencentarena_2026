### 2.2 赛题任务（写作背景，直接采用）

- 智能体：单英雄"小胖鹅"，在 **128×128** 栅格地图中活动，单局最多 **1000 步**。
- 目标：躲避 **2 只怪物**追击，并尽可能多地收集宝箱。
- 动作空间 **16 维**：`0–7` 八方向移动；`8–15` 八方向空间穿梭（直线 10 格 / 斜向 8 格，冷却 100 步）。
- 观测：英雄局部视野（POMDP），`map_info` 为局部栅格视图（栅格视图 21×21；`visit_view_mask` 为 11×11，见 6.2）。
- 第 2 只怪物默认 **300 步**出现（`monster_interval=300`）；怪物默认 **500 步**后加速（`monster_speedup=500`，速度 1→2 格/步，快于英雄）。
- 计分：`总分 = 存活步数 × 1.5 + 宝箱数 × 100`。

### 2.3 算法与技术栈

- 算法：**PPO**（clip 目标）+ **RND**（随机网络蒸馏，内在好奇心奖励）+ **辅助任务**（怪物位置预测 / 安全区域分类 / 动作方向建议）。
- 价值函数：**三头 value**（`VALUE_NUM = 3`，`conf.py:47`），三路分别对齐 `[step, treasure, survive]` 三类奖励。
- 分布式训练：基于 kaiwudrl 框架的 Actor-Learner 异步架构（见 `app_conf_gorge_chase.toml` 的 `AsyncBuilder`）。

### 4.2 框架如何找到我们的代码

`run_train_test(algorithm_name="ppo")` 之后，kaiwudrl 框架读取两份契约配置：

- `conf/algo_conf_gorge_chase.toml`：把算法名 `ppo` 映射到具体的类路径。
  - `actor_agent` / `learner_agent` / `aisrv_agent` 均为 `agent_ppo.agent.Agent`（第 2–4 行）。
  - `train_workflow = "agent_ppo.workflow.train_workflow.workflow"`（第 5 行）。
  - `eval_workflow` / `exam_workflow` 指向框架内置的 `tools.eval.*`（第 6–7 行）。
- `conf/app_conf_gorge_chase.toml`：
  - `[gorge_chase]` → `rl_helper = "kaiwudrl.server.aisrv.kaiwu_rl_helper_standard.KaiWuRLStandardHelper"`（第 2 行）。
  - `[gorge_chase.policies.train_one]` → `policy_builder = "...async_policy.AsyncBuilder"`、`algo = "ppo"`（第 5–6 行）。

即：**同一个 `Agent` 类同时扮演 Actor、Learner、Aisrv 三种角色**（同一份代码被不同进程加载），由框架进程角色区分行为。

### 6.1 `agent_ppo/agent.py`

| `class Agent(BaseAgent)` | 44 | 智能体主类 |

| `Agent.reset` | 68 | 重置预处理器与统计量 |

| `Agent.exploit` | 140 | 评估用贪心动作 |
| `Agent.learn` | 152 | 转交 `Algorithm.learn` |

| `Agent.load_model` | 169 | 读 ckpt |

| `Agent.action_process` | 202 | 取出动作并写回 `last_action` |

**核心逻辑**：

1. `__init__`（L45）：固定随机种子 `torch.manual_seed(0)`（L46），构建 `Model(device)`（L48）与 Adam 优化器（L51，`lr = Config.INIT_LEARNING_RATE_START = 3e-4`，`betas=(0.9,0.999)`）；再实例化 `Algorithm`（L56）与 `Preprocessor`（L57）；维护三路奖励累计器 `step/treasure/survive_reward_sum`（L62-64）；最后调用 `super().__init__`（L66）。

2. `_predict_with_model`（L79）：把 `feature` 变成 `(1, 480)` 的 float tensor（L85），在 `torch.no_grad()` 下 `self.model(obs_tensor, inference=True)`（L88）。输出是 7 元组，注释在 L90-91 明确顺序：`[logits, value, target, predict, monster_pred, safety_pred, action_hint]`。其中 `target/predict` 各 256 维（RND 全连通输出），`monster_pred` 8 维、`safety_pred` 4 维、`action_hint` 8 维。

3. `predict`（L106）：先取 `list_obs_data[0]` 的 `feature` 与 `legal_action`（L111-112）；`_legal_soft_max` 得到概率分布（L121），再分别用 `use_max=False` 采样得到 `action`、`use_max=True` 得到 `d_action`（贪心，用于评估）（L122-123）；把 `action/d_action/prob/value/target/predict/monster_pred/safety_pred/action_hint` 打包进 `ActData`（L125-137）。

4. `observation_process`（L178）：调用 `self.preprocessor.feature_process(env_obs, self.last_action)`（L183），拿到 `(feature, legal_action, reward, aux_labels)`；把 `aux_labels` 与 `reward` 放进 `remain_info`；返回 `ObsData(feature, legal_action, sub_action_mask=[1]*Config.NUMB_HEAD)`，`NUMB_HEAD = 1`（`conf.py:14`）。

5. `_legal_soft_max`（L215）：常量 `_lsm_const_w=1e20, _lsm_const_e=1e-5`（L220）；`tmp = input_hidden - 1e20*(1-legal_action)`（L222）把非法动作压到极小；数值稳定后 `exp`，再乘 `legal_action` 清零非法项，最后归一化并乘 `1.00001` 防除零（L224-226）。

6. `action_process`（L202）：`is_stochastic=True` 用 `act_data.action`，否则用 `d_action`；把 `last_action` 更新为 `int(action[0])` 并返回（L212-213）。**注意**：该 `last_action` 会传给下一步 `feature_process`，用于"卡住检测"（见 6.2 的 `get_legal_action`）。

### 6.2 `feature/preprocessor.py`（核心，1059 行）

**职责**：整个项目的"神经中枢"。把原始 `env_obs` 解析为结构化状态，生成 **480 维观测特征**、**16 维合法动作掩码**、**3 路奖励**、**20 维辅助任务标签**。后续 v1~v5 的奖励工程几乎都在这个文件里进行。

- **主 MLP**：`main_mlp_net = MLP([64*9, 512, 256], non_linearity_last=True)`（L195）。输入是 `attended(64) + dist + global + visited + progress + temporal + path_planning + treasure_priority + safety_heatmap` = 9×64 = 576（L284-297）。
- **Actor 头**：`label_mlp = MLP([256,64,16])`（L199），经 `process_legal_action`（L217-222）后 softmax。
- **独立 Critic**：`CriticNetwork(feature_dim=64*9=576, value_num=3, hidden_dims=[512,256,128])`（L203-207）；backbone 为 `Linear→ReLU→LayerNorm` 堆叠（L76-84），`value_head=Linear(128→64)→ReLU→Linear(64→3)`（L86）。

  - `monster_pred_head`：256→128→64→`num_monsters*4=8`；

- **RND**：`RNDNetwork(self.feature_len=480)`（L215），返回 `(target, predict)`，各 256 维。

**`forward`（L326）输出**：
- `inference=True` → `[logits, value, target, predict, monster_pred, safety_pred, action_hint]`（L346-348）；

### 6.6 `algorithm/algorithm.py`（219 行）

**职责**：把一批 `SampleData` 转成张量，计算 **PPO + RND + 辅助任务**总损失并反传。

| 符号 | 行号 | 说明 |
| --- | ---: | --- |
| `Algorithm.__init__` | 23 | 记录超参、辅助损失权重 |
| `Algorithm.learn` | 47 | 组装批量 → 前向 → 损失 → 反传 → 上报 |
| `Algorithm._compute_loss` | 127 | 各类损失计算 |
| `Algorithm._masked_softmax` | 210 | 掩码 softmax |

**`learn`（L47）关键步骤**：

1. 把 `list_sample_data` 各字段 `torch.stack` 成批量（L52-61），其中 `aux_labels` 来自样本。
2. `set_train_mode()` + `zero_grad()`（L65-66），`rst_list = self.model(obs)`（L70，注意此处 `inference=False`，返回 `label_out`）。
3. `_compute_loss(...)`（L75-86）得 `total_loss`；`total_loss.backward()`（L91）。
4. 梯度裁剪：`USE_GRAD_CLIP=True`、`GRAD_CLIP_RANGE=0.5`（`conf.py:81-82`），用 `clip_grad_norm_`（L95-96）；`optimizer.step()`（L98）。
5. 每 **60 秒** 上报一次监控（L109-125）：`value_loss / policy_loss / entropy_loss / rnd_loss / aux_loss / reward`，并 `monitor.put_data({os.getpid(): results})`。

**`_compute_loss`（L127）**：

- 价值目标 `tdret = reward_sum`（L144，即 GAE 回报）。
- **价值损失（clip）**：`value_clip = old_value + clip(value_pred - old_value, ±clip_param)`，`value_loss = 0.5 * max((tdret-value_clip)^2, (tdret-value_pred)^2).mean()`（L153-158）。三头 value 一起算（维度 3 被 `squeeze`）。
- **策略损失（PPO clip）**：`prob_dist = _masked_softmax(label_out, legal_action)`（L162）；`ratio = new_prob / old_prob`（L171）；优势对三通道取均值 `adv_for_policy = adv_squeezed.mean(dim=-1)`（L174）；`policy_loss = max(-ratio*adv, -clip(ratio,1±clip_param)*adv).mean()`（L178-180）。
- **熵损失**：`entropy_loss = -Σ p*log p`（L164，作为**奖励项**，故最终损失中是 `- var_beta * entropy_loss`）。
- **RND 损失**：`rnd_loss = mean((target - predict)^2)`（L184）。
- **辅助损失**（L188-201）：`aux_labels` 拆成 `monster(0:8)` / `safety(8:12)` / `action_hint(12:20)`；分别用 MSE / BCE / MSE，权重各 **0.1**（`self.aux_monster_loss_weight` 等，L40-42）。
- **总损失**（L203）：`total_loss = vf_coef*value_loss + policy_loss - var_beta*entropy_loss + rnd_loss + aux_loss`，其中 `vf_coef=1`（`conf.py:72`），`var_beta=BETA_START=5e-4`（`conf.py:64`）。
- `info_list`（L205-206）：`[tdret.mean(), value_loss, policy_loss, entropy_loss, rnd_loss, aux_loss, adv.mean(), adv.std(), reward.mean()]`，供 `learn` 上报使用。

## 10. 设计评价：优点 / 风险 / 可改进点

### 10.1 优点

1. **工程骨架完整、契约清晰**：`algo_conf` / `app_conf` / `configure_app` 三张表把"用什么 Agent、跑什么 Workflow、怎么异步训练"解耦得很干净；`train_test.py` 与平台训练共用同一份 Agent 代码。
2. **特征工程覆盖充分**：480 维观测把"位置 / 距离 / 方向 / 速度 / 危险度 / 路径安全 / 安全热力图 / 访问图"都编码进去了，还为 POMDP 补了时序轨迹（`temporal 24D`），起手难度低。
3. **显式的占位设计**：把奖励留白并用 `TODO` 标注，意图明确、便于教学与选手对齐；辅助任务（预测怪物/安全/动作建议）也提供了稠密的学习信号。
4. **网络结构分工明确**：子 MLP 分模态编码 + 注意力做跨模态融合 + **独立 Critic**（减少梯度干扰）+ RND（探索），是较成熟的设计范式。
5. **三头 value 与三类奖励对齐**：`VALUE_NUM=3` 与 `reward=[step,treasure,survive]` 逐通道对应，GAE 逐通道计算，便于分别调节。

### 10.2 风险与隐患

1. **奖励稀疏、策略性奖励缺失**：宝箱权重 0、穿梭/时机/探索/buff 均为 TODO → 默认配置下智能体几乎没有"收集宝箱""用穿梭逃逸"的动力，容易学到"原地苟到 1000 步"的保守策略（因为终局 `truncated` 给了 `+20`）。
2. **终局奖励落在 survive 通道**（`train_workflow.py:187/193`）：`final_reward` 为 `[0,0,x]`，与"存活"语义一致，但 `+20` 的大额正奖励会主导 survive 价值头，可能压制其它通道的学习。
3. **硬编码常量散落**：`_get_treasure_priority_feature` 里 `monster_speed=1.5`（L499）、`bucket_centers`（L266）、各归一化上限（180/60/30/50 等）多处在函数体内硬编码，缺乏集中配置，调参时容易漏改。
4. **`get_legal_action` 的卡住检测较激进**：只要位置差分 `<0.001` 就把 `last_action` 永久加入 `bad_move_ids`（L983-990），在某些"贴墙平移"场景可能误封合法动作；虽有全禁回退（L996-998），但仍会引入额外的探索噪声。
5. **`frame_no` 与 `step_no` 同源**：`frame_no = step_no`（L736），而 `frame_no_norm = norm_val(frame_no, 3000)`（L737），归一化上限 3000 与实际最大 1000 不匹配（终局 `survival_factor` 依赖它，取值偏小）。
6. **RND 奖励被裁剪到 0.1 并加到 step 通道**（`train_workflow.py:160`）：`target/predict` 是 256 维向量的 MSE 均值，量级与手工奖励不同尺度，需要留意其主导性。
7. **监控上报存在时间窗**：`algorithm.py` 与 `workflow` 均以 60 秒为最小上报间隔（L110 / L82 / L253），短局训练时监控点会稀疏。
8. **`ObsData` 的 `sub_action_mask` 恒为 `[1]*NUMB_HEAD`**（`agent.py:194-197`，`NUMB_HEAD=1`）：该字段实际未被模型使用（`model.py` 前向未接收它），属冗余。

### 10.3 可改进点（后续版本的方向）

- 填充第 9 章 5 处 TODO，尤其是**宝箱权重**与**探索奖励**，为策略提供直接梯度。
- 把硬编码常量（怪物速度、归一化上限、距离桶中心）抽到 `Config`，便于统一调参。
- 复核终局奖励的通道归属与量级，避免单通道奖励失衡。
- 校正 `frame_no_norm` 的归一化上限（应贴合 `max_step=1000`）。
- 清理 `random_choice` 等遗留未用代码。
