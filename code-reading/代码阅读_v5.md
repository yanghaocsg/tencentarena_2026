## 2. 版本概览

### 2.1 设计目标

- v1→v4 靠**逐帧奖励 shaping** 稳步提升（v4 50 局评估总分 1004.46、终止步数 365.64），但边际收益已经很小，且平均仍只活约 365 步（死在第二只怪 300 步出现后的双怪包夹，活不到 500 步加速）、方差极大、无 WIN、buff 几乎不捡。
- v5 的判断是：这些是**探索/样本结构**问题——智能体在掌握基础走位前就被投进完整双怪+加速环境，早期高死亡率导致"双怪落点、捡 buff、后期生存"的正样本太少。
- 因此 v5 引入课程学习：**由易到难安排环境配置**，让每个阶段集中产出对应技能的正样本，目标突破 365 步并出现 WIN。

### 4.2 episode_cnt 如何流经 workflow → curriculum → env.reset

这是 v5 的**唯一新增控制流**，也是本篇重点。调用链（行号来自 `train_workflow.py`）：

```text
workflow(envs, agents, ...)                              # L26
  └─ read_usr_conf("agent_ppo/conf/train_env_conf.toml") # L33  → usr_conf
  └─ EpisodeRunner(env, agent, usr_conf, logger, monitor) # L40
       └─ __init__: self.episode_cnt = 0                  # L70
       └─ run_episodes()  (生成器，逐局 yield)             # L74
            while True:
              ① stage_name = get_stage_name(self.episode_cnt)          # L91  ← 课程判定
              ② cur_conf  = build_curriculum_conf(self.usr_conf,
                                                   self.episode_cnt)     # L92  ← 覆盖配置
              ③ env_obs   = self.env.reset(cur_conf)                    # L93  ← 注入环境
              ④ handle_disaster_recovery(env_obs, logger)               # L97
              ⑤ agent.reset(env_obs); agent.load_model(id="latest")     # L102-103
              ⑥ obs_data, remain_info = agent.observation_process(env_obs)# L107
              ⑦ self.episode_cnt += 1                                   # L116 ← 计数自增
              ⑧ logger.info("Episode {N} stage {stage_name} start, usr_conf is {cur_conf}")  # L121-123
              while not done: ...   # 逐帧交互、奖励、GAE、yield collector
```

**关键点**：

- `get_stage_name` / `build_curriculum_conf` 都在 `env.reset` **之前**调用，`env.reset(cur_conf)` 收到的是本局（本阶段）覆盖后的配置。
- `episode_cnt` 在 `env.reset` 之后、进入逐帧循环之前自增（L116）。因此第 1 局的判定用的是 `episode_cnt = 0`（阶段 0），第 601 局的判定用 `episode_cnt = 600`（进入阶段 1），边界与 `STAGES` 的上界语义一致。
- 日志（L121-123）在自增之后打印，所以 `Episode 1 ... stage 0_single`；训练日志里 `stage` 字段随局数依次出现 `0_single → 1_dual_nospeed → 2_dual_speed → 3_full`，是监控课程是否推进的**快信号**。

### 4.3 workflow 外层循环

`workflow`（L48-60）无限循环消费 `episode_runner.run_episodes()` 生成器，每收到一局样本（`g_data`）就 `agent.send_sample_data(g_data)` 送给 learner，并每 1800 秒 `agent.save_model()`。

### 6.1 agent_ppo/conf/curriculum.py（新增模块，逐一函数精读）

#### 6.1.1 模块头与设计意图（L6-15）

#### 6.1.2 STAGES 常量（L20-61）

`STAGES` 是 `list[tuple[int, dict]]`，**每个 tuple 的第一个元素是该阶段局数上界（不含）**，第二个是该阶段的配置覆盖字典：

| 元素 | 上界 `end_episode` | overrides | 行号 |
| :-- | --: | :-- | :-- |
| 阶段 0 | 600 | `{"monster_interval": 2000, "monster_speedup": 2000, "treasure_count": 6}` | L26-33 |
| 阶段 1 | 1800 | `{"monster_interval": 150, "monster_speedup": 2000, "treasure_count": 10, "buff_count": 2, "buff_cooldown": 50}` | L37-46 |
| 阶段 2 | 3000 | `{"monster_interval": 300, "monster_speedup": 500, "treasure_count": 10, "buff_count": 2, "buff_cooldown": 200}` | L49-58 |
| 阶段 3 | —（隐式） | 无 overrides（无 tuple，代表 ≥3000） | L59-60 注释 |

设计细节：
- 阶段 0 的 `monster_interval = 2000 > max_step = 1000`，等价"第二怪永不出现"；`monster_speedup = 2000` 同理"局内不加速"。
- 阶段 1 把第二怪提前到 150 步（拉长双怪练习窗口），但仍不加速；`buff_cooldown = 50` 让 buff 高频刷新以练"捡 buff"，呼应 v4 的 buff 拾取/靠近奖励。
- 阶段 2 恢复完整怪物节奏（300 出现、500 加速），专练后期生存。
- 阶段 3 无 tuple 项，靠 `get_stage_index` 返回 `len(STAGES)` 表示"超出所有阶段"。
- 注释 L21-22 声明所有取值均在 `train_env_conf.toml` 官方合法范围内（第 10 章核对）。

#### 6.1.3 STAGE_NAMES（L63）

#### 6.1.4 get_stage_index（L66-71）

```python
def get_stage_index(episode_cnt: int) -> int:
    for i, (end_episode, _) in enumerate(STAGES):
        if episode_cnt < end_episode:
            return i
    return len(STAGES)
```

线性扫描，返回第一个满足 `episode_cnt < end_episode` 的下标；都不满足则返回 `len(STAGES) = 3`（终段）。**边界语义**：`episode_cnt ∈ [0,599]→0`、`[600,1799]→1`、`[1800,2999]→2`、`≥3000→3`。注意参数是"已完成局数"，与 4.2 中"自增前判定"配合，使第 601 局恰好进入阶段 1。

#### 6.1.5 get_stage_name（L74-75）

```python
def get_stage_name(episode_cnt: int) -> str:
    return STAGE_NAMES[get_stage_index(episode_cnt)]
```

把下标映射为可读名字，供 workflow 日志使用。

#### 6.1.6 build_curriculum_conf（L78-104）

```python
def build_curriculum_conf(base_conf, episode_cnt):
    stage = get_stage_index(episode_cnt)          # L85
    if stage >= len(STAGES):                      # L88 终段
        return base_conf                          # L89 原样返回
    overrides = STAGES[stage][1]                  # L91
    conf = copy.deepcopy(base_conf)               # L92 深拷贝，避免污染基础配置
    if isinstance(conf, dict) and isinstance(conf.get("env_conf"), dict):  # L94
        target = conf["env_conf"]                 # L95 嵌套结构
    elif isinstance(conf, dict):                  # L96
        target = conf                            # L97 扁平结构
    else:
        return base_conf                         # L99 非 dict 直接返回
    for key, value in overrides.items():         # L101
        if key in target:                        # L102 只覆盖已存在的键
            target[key] = value
    return conf
```

要点：
- **终段短路**（L88-89）：`stage >= len(STAGES)` 时原样返回，不 deepcopy、不覆盖——保证阶段 3 完全等于 `train_env_conf.toml`。
- **两种结构自适应**（L94-99）：kaiwu 的 `read_usr_conf` 返回 `{"env_conf": {...}}` 嵌套结构时改内层；若传入扁平 dict 则直接改自身；既非 dict 也非嵌套则原样返回（防御）。这是考虑到 `usr_conf` 的真实结构可能随框架版本变化。
- **深拷贝**（L92）：`copy.deepcopy` 保证 `self.usr_conf` 不被原地修改，下一局仍以干净的基础配置为底稿。
- **只覆盖已存在键**（L102）：`if key in target` 保证不会向配置中注入非法/未知字段——若基础配置缺少某键，则该覆盖静默失效（这是一个值得注意的"静默失败"点，第 10 章讨论）。

#### 6.3.2 v5 相位对齐：`_get_threat_timings`（L649-659，新增）

```python
def _get_threat_timings(self):
    """Return (second_monster_step, speedup_step) from env_info with safe fallbacks.
    从 env_info 读取(第二怪出现步, 加速步)；缺失或非法(-1/None)时回退到比赛默认 300/500。
    """
    info = getattr(self, "env_info", None) or {}          # L654
    interval = info.get("monster_interval")               # L655
    speedup = info.get("monster_speedup")                 # L656
    interval = interval if isinstance(interval, (int, float)) and interval > 0 else 300   # L657
    speedup = speedup if isinstance(speedup, (int, float)) and speedup > 0 else 500       # L658
    return int(interval), int(speedup)                    # L659
```

**为什么需要它**：v4 把相位阈值硬编码为 `phase1_end = 300 / phase2_end = 500`（对应基础 toml 的 `monster_interval=300`、`monster_speedup=500`）。v5 课程阶段 1 把 `monster_interval` 改成 150、阶段 0 改成 2000，若仍用 300/500，则"收集/生存权重切换点"会与实际威胁出现时间错配。该函数从环境回传的 `env_info` 读取**实际**的怪物时序，实现奖励相位与当前阶段对齐。

**取值来源**：`self.env_info` 在 `pb2struct` L916 处由 `obs.get("env_info")` 赋值，所以 `_get_threat_timings` 依赖 `pb2struct` 已被调用（`reward_process` 在 `feature_process` 内、`pb2struct` 之后调用，满足）。

**回退逻辑**：`interval` 非 `int/float` 或 ≤0（含 `-1` 表示随机的官方语义、`None`）时回退 300；`speedup` 同理回退 500。这保证在 `env_info` 缺失或阶段 0 的 `2000` 等取值下都能返回有效整数。注意：阶段 0 的 `monster_interval=2000`、`monster_speedup=2000` 均为合法正数，会**原样返回 2000**，即整局都停留在相位 1（collect 权重最高）——这正是课程设计意图（单怪阶段以收集/探索为主）。

#### 6.3.3 `_calc_phase_reward`（L635-647，v5 改为读取实际阈值）

```python
def _calc_phase_reward(self, frame_no: int, max_step: int = 1000) -> Dict[str, float]:
    phase1_end, phase2_end = self._get_threat_timings()   # L640  ← v5 改动
    if frame_no < phase1_end:
        return {"collect": 1.2, "survive": 0.8, "explore": 1.0}   # L643
    elif frame_no < phase2_end:
        return {"collect": 1.0, "survive": 1.0, "explore": 0.8}   # L645
    else:
        return {"collect": 0.7, "survive": 1.3, "explore": 0.5}   # L647
```

三段相位权重：**第二怪出现前**偏收集/探索（collect 1.2、explore 1.0、survive 0.8）；**第二怪出现后、加速前**均衡（1.0/1.0/0.8）；**加速后**偏生存（collect 0.7、survive 1.3、explore 0.5）。v5 只是把两段分界从常量改为 `_get_threat_timings()` 返回值。

#### 6.3.4 `_calc_flash_landing_reward`（L707-735，v5 改 is_dual_phase 判定）

穿梭（flash/shuttle）落点奖励，v4 已有，v5 改一行判定：

```python
safety_gain = self.dual_safety - self.last_dual_safety                      # L715
escape_options, _ = detect_dead_ends(self.map_data[0], self.cur_pos)        # L716
second_monster_step, _ = self._get_threat_timings()                         # L717  ← v5 新增

        return min(1.0, 0.4 + 2.0 * safety_gain)     # L724 双怪阶段成功逃到开阔区
    if escape_options < 3:
        return -0.3                                   # L726 落点死角
    if safety_gain < 0:
        return -0.2                                   # L728 落点更危险

else:
```

### 6.4 algorithm/algorithm.py（沿用 v4，含 advantage 标准化）

共 223 行，**与 v4 逐字节一致**（MD5 相同）。是 PPO + RND + 辅助任务的损失实现。

- **`learn`（L47-125）**：把一 batch `SampleData` 堆叠成 tensor（L52-61）→ 前向 `self.model(obs)`（L70）→ `_compute_loss`（L75-86）→ `total_loss.backward()`（L91）→ 梯度裁剪 `clip_grad_norm_(params, GRAD_CLIP_RANGE)`（L95-96）→ `optimizer.step()`（L98）→ 每 60 秒上报 monitor（L109-125）。
- **`_compute_loss`（L127-212）**：
  - value loss 用 clipped 形式（L153-158），target 为 GAE 的 `reward_sum`（L144）。
  - policy loss：masked softmax（L162）→ ratio（L167-171）→ **advantage batch 标准化**（L180）：

    ```python
    adv_for_policy = (adv_for_policy - adv_for_policy.mean()) / (adv_for_policy.std() + 1e-8)
    ```

    这是 v2 引入、v4/v5 沿用且判定正确的稳定化做法；三头平均后尺度统一，显著降低策略震荡。

  - 辅助任务 loss（L193-205）：monster(8) 用 MSE、safety(4) 用 BCE（clamp 到 [0,1]）、action_hint(8) 用 MSE，权重均 0.1（L40-42）。

- **`_masked_softmax`（L214-223）**：`label + 1e5*(legal_action-1)` 把非法动作概率压到 0。

## 10. 设计评价：优点 / 风险 / 可改进点

### 10.1 优点

1. **最小侵入**：只新增 1 文件、改 2 文件 4 处；`algorithm/agent/model/conf/diy` 全不动，回归风险低，便于与 v4 对照。
2. **纯函数、易测**：`curriculum.py` 无全局状态，`get_stage_index/get_stage_name/build_curriculum_conf` 可独立单测（文档已报告边界 599/600、1799/1800、2999/3000 切换正确）。
3. **健壮的结构自适应**：`build_curriculum_conf`（L94-99）同时支持扁平 dict 与 `{"env_conf": {...}}` 嵌套，规避框架 `read_usr_conf` 返回结构差异。
4. **相位真正对齐**：`_get_threat_timings`（L649-659）让奖励相位由"实际怪物时序"驱动，而非硬编码，是本版本对奖励 shaping 的实质增强。
5. **可读性好**：`STAGES` 表把"阶段边界 + 覆盖参数"集中为常量（L23-61），调整课程只需改一处。
6. **params 合法**：所有覆盖值均落在官方范围内（见 10.3）。

### 10.2 风险

1. **进度信号是每 worker 局部的 `episode_cnt`**（L70、L116）：多 worker 下各 worker 独立推进；若某 worker 进程重启（容灾恢复），计数从 0 重来，该 worker 会**退回阶段 0**，造成全局训练分布不一致、进度回退。建议改用 learner 侧 `global_step` 或可持久化的全局进度。
2. **静默失效**：`if key in target`（L102）在键不存在时静默跳过覆盖；且不校验覆盖值合法性。若基础 toml 改键名，课程会"看起来在跑但实际没覆盖"。
3. **训练/评估分布不一致**：课程仅在 `train_workflow` 生效；eval/exam 工作流（`tools.eval.*`，见 `algo_conf` L6-7）用基础 toml（300/500/10 箱）。阶段 0/1 的特征分布（如 `_get_progress_feature` 的 `second_monster_countdown`、`treasure_progress` 分母）与评估环境不同，存在 train-test mismatch；阶段 3 才完全一致。
4. **阶段硬切换无退火**：600/1800/3000 处参数瞬间跳变，可能带来性能突降（如阶段 1→2 恢复加速）。
5. **固定局数边界与实际收敛脱钩**：若训练时长短或 worker 数少，可能到不了阶段 2/3（仍停在易阶段，评估时性能差）；若某阶段早已掌握，则浪费样本。

### 10.3 课程边界与官方参数合法范围

**边界 600/1800/3000 的合理性**：
- 阶段 0（600 局）目的是把基础走位/收集练稳：500 步加速前、单怪无压力，600 局足以形成正样本；600 局 × 约 365-1000 步 ≈ 22-60 万步/worker。
- 阶段 1（1200 局，600→1800）练双怪+捡 buff，窗口最长，符合"双怪落点/捡 buff 是短板"的诊断；`buff_cooldown=50` 使 buff 高频刷新，正样本产出足够。
- 阶段 2（1200 局，1800→3000）专练 500 步加速后的后期生存。
- 阶段 3（≥3000）在比赛配置上精调。
- 边界是"经验值 + 可调常量"（文档 §2 亦说明可按训练时长/收敛速度调整），无理论最优保证。

**与官方合法范围核对（`train_env_conf.toml`）**：

| 课程覆盖项 | 取值 | 官方范围 | 是否合法 |
| :-- | --: | :-- | :-- |
| `monster_interval` | 2000 / 150 / 300 | -1, 11~2000 | ✅ |
| `monster_speedup` | 2000 / 500 | -1, 1~2000 | ✅ |
| `treasure_count` | 6 / 10 | 0~10 | ✅ |
| `buff_count` | 2 | 0~2 | ✅ |
| `buff_cooldown` | 50 / 200 | 1~500 | ✅ |
| `talent_cooldown` | 未覆盖（100） | 100~2000 | ✅（不缩短技能 CD） |

### 10.4 可改进点

1. **进度信号全局化**：用可持久化的全局完成局数或 learner `global_step`，避免 worker 重启导致阶段回退。
2. **自适应推进**：以"阶段内平均存活步/死亡率/buff 获取率"为判据推进，而非纯局数。
3. **显式终段**：在 `STAGES` 中显式写阶段 3（或引入 `FINAL_STAGE_MARKER`），而非依赖 `len(STAGES)` 隐式约定。
4. **切换平滑**：阶段切换处对参数做线性/退火过渡，降低跳变。
5. **配置校验**：`build_curriculum_conf` 增加"未命中键"告警，避免静默失效。
6. **train/eval 对齐**：评估阶段也应复用同一 curriculum 阶段（或在阶段 3 之后再评估），减少 mismatch。
7. **文档化进度**：把每 worker 的 `episode_cnt` 纳入 monitor（当前 monitor 上报包含 `episode_cnt`，见 workflow L261，可用于核对课程进度——此点已有基础）。
