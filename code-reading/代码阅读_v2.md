## 1. 本篇定位与阅读路线

### 1.1 v2 是什么

v2 是「峡谷追猎」PPO 训练工程从 v1 走向 v4/v5 过程中的**第二个迭代版本**。它的设计动机来自 v1 诊断出的两条根因链：

1. **核心技能冷启动**：空间穿梭（flash）CD 长（100 步）、开局不可用，随机策略下「用穿梭→成功逃生」的正样本极稀疏，且 v1 给的奖励上限只有 0.5，作者判断形成「冷启动死循环」。buff（加速）同理几乎不捡。
2. **PPO 缺少 advantage 标准化**：三个 value 头（step / treasure / survive）的 advantage 简单平均后**尺度不统一**，导致策略更新方向抖动、方差大、进入平台期。

v2 针对这两条根因做了**最小对症改动，只改 2 个文件**：

- `agent_ppo/feature/preprocessor.py`：提高穿梭成功奖励、加重失败惩罚、新增「机会成本」惩罚、把 buff 奖励从 treasure 通道改到 survive 通道并加强。
- `agent_ppo/algorithm/algorithm.py`：policy 使用 advantage 前做 **batch 内标准化**。

### 1.2 一个必须辩证看待的事实

v4 文档《PPO_v4_设计与优化路线.md》复盘指出：**v2 基于「监控总览闪现图为 0」判断「穿梭从不使用」是一次误判**。

- 监控总览「闪现」曲线用的是 `flash_count` 的**速率/每帧指示**（≈3.7 次摊到一整局，曲线贴 0），而评估页的「技能使用次数」是**每局累计**，两者口径不同。
- 实测两个模型（v1/v2）**一直在 CD 一好就用穿梭**（≈1.1 次/百步，CD=100 步，已到使用上限）。
- 因此 v2 的「冷启动激励」在**方向上错了**（v4 已删除这批改动：穿梭成功/失败奖励与「危险不用技能 −0.05」机会成本），但 **advantage batch 标准化是正确的独立修复**（v4/v5 保留）。

本篇对 v2 的评述将**如实区分这两类改动**：一类是已被证伪的冷启动激励，一类是被后续版本保留的 PPO 稳定性修复。二者的效果在 v2 的评估数据里是**耦合的、无法单独归因**的——这一点在 §10 展开。

### 4.4 关键点

- **每次对局开始**才 `load_model(id="latest")`（train_workflow.py:100），保证 actor 拿到 learner 最新参数。
- **每 1800s** 保存一次模型（train_workflow.py:57-59）；leaner 侧按 `dump_model_freq` 推送。
- 每个 step 都会重新跑一次 `observation_process`，即**特征处理发生在 `env.step` 之后**（用新观测算旧动作的奖励）。因此 `reward_process` 里用的是 `self.last_action`（上一步动作）。
- **终局奖励**不进入 `reward_process`，而是在 workflow 里对 collector 最后一帧追加（train_workflow.py:250）。

### 5.1 三维奖励的通道约定（关键）

在 `reward_process` 返回值与 workflow 中，**固定顺序**为：

| 下标 | 通道名 | 语义 | 在 workflow 中的累计变量 |
|---|---|---|---|
| 0 | step | 步数/探索/穿梭即时奖励 | `agent.step_reward_sum`（train_workflow.py:164） |
| 1 | treasure | 宝箱相关奖励 | `agent.treasure_reward_sum`（:165） |
| 2 | survive | 生存/buff/机会成本 | `agent.survive_reward_sum`（:166） |

> 这三个通道同时对应 `SampleData.reward / reward_sum / value / advantage` 的 `VALUE_NUM = 3` 维（conf.py:47）。
> RND 内在奖励只叠加到 `reward[0]`（step 通道，train_workflow.py:160）。

### 6.2 feature/preprocessor.py（★ 核心，篇幅最大）

`preprocessor.py`（1098 行）是 v2 的**主战场**：所有冷启动激励改动都在这里。它有三个职责：**① env_obs → 480D 特征；② 生成 20D 辅助任务标签；③ 计算三维奖励**。

#### 6.2.1 类结构与状态（reset，142-201）

#### 6.2.2 特征生成（feature_process，852-994）

`feature_process` 的流程：

1. `self.last_action = last_action`（863），随后 `pb2struct(obs)`（864）解析结构化信息。
2. 计算 8 方向 **射线距离** `ray_dist`（869-886）与 **穿梭距离** `flash_dist`（890-908）。
3. `get_legal_action()`（912）——合法动作掩码。
4. 依次生成各子特征，最后 `np.concatenate` 拼成 480D（947-983）。
5. 生成 20D 辅助标签（987）并返回 `(feature, legal_action, reward_process(), aux_labels)`（989-994）。

**480D 特征拼接顺序**（对照 conf.py:21-33 的 `FEATURES`）：

| 序 | 子特征 | 维度 | 生成位置 | 说明 |
|---|---|---|---|---|
| 1 | treasure_pos | 6×13=78 | 811-816 | 每个宝箱 6D `_get_pos_feature`，取最近 13 个，不足补位 |
| 2 | buff_pos | 6 | 807 | buff 相对位置特征 |
| 3 | buff_status+cd | 2 | 951-956 | `[buff_status, norm(cooldown,100)]` |

#### 6.3.3 _compute_loss（127-212）

**value 目标**：`tdret = reward_sum`（144，即 GAE 累积回报 `gae + value`，由 definition.py 计算）。

**value loss（裁剪式，153-158）**：
```
value_clip = old + clamp(value - old, -0.2, 0.2)
value_loss = 0.5 * max( (tdret-value_clip)^2 , (tdret-value)^2 ).mean()
```
> 三头 value 一起算同一份 loss（`value_pred`/`old_value`/`tdret` 均为 `VALUE_NUM=3` 维）。

**policy loss（PPO clip，160-184）**：
```
prob_dist = masked_softmax(label_out, legal_action)     # 162, 214-223
entropy_loss = -Σ p·log p                                 # 164
ratio = new_prob / old_prob                               # 171
adv_for_policy = adv_squeezed.mean(dim=-1) if 多维 else unsqueeze  # 173-176
adv_for_policy = (adv_for_policy - mean) / (std + 1e-8)   # ★v2 新增，180
policy_loss = max(-ratio*adv, -clamp(ratio,0.8,1.2)*adv).mean()  # 182-184
```

**RND loss**：`mean((target - predict)^2)`（188）。

**辅助任务 loss（192-205）**：把 `aux_labels[:, :20]` 切成 monster(8)/safety(4)/action_hint(8)，分别 MSE/BCE/MSE，各乘 0.1 权重求和。

**total_loss（207）**：
```
total_loss = vf_coef*value_loss + policy_loss - var_beta*entropy_loss + rnd_loss + aux_loss
```

#### 6.3.4 ★ advantage 标准化的位置与作用（180）

```
adv_for_policy = adv_squeezed.mean(dim=-1, keepdim=True)   # 173-174 三头平均 → 标量
adv_for_policy = (adv_for_policy - adv_for_policy.mean()) / (adv_for_policy.std() + 1e-8)  # 180 v2
```

**位置**：在「三头 advantage 平均」之后、「PPO ratio 相乘」之前。也就是说，标准化作用在**送进 policy loss 的那一路优势**上。

**作用与边界**：

- **只影响 policy**：value loss 用的是 `tdret`（原始 GAE return，144），**未标准化**（v2 文档 §三 明确「三头各自的 value 学习不受影响」）。
- **解决尺度不统一**：三个 value 头（step/treasure/survive）的量级差异很大（treasure 通道动辄 ±1.0，survive 通道基准仅 0.02），简单平均后 advantage 的尺度/偏移不稳定；标准化把每批优势归一到均值 0、方差 1，使 `clip_param=0.2` 的裁剪区间、以及 policy 梯度步长**稳定在可比尺度**上，减少更新方向抖动。
- **它是常规 PPO 做法**：主流 PPO 实现（如 OpenAI baselines / Stable-Baselines3）默认都会对 advantage 做 batch 归一化。
- **一个尺度细节（需注意）**：本框架里 `learn()` 的输入 batch 来自 `send_sample_data(episode_data)`，即**一个 episode 的帧序列**（train_workflow.py:51）。因此这里的「batch 标准化」实际近似 **episode 内标准化**，而不是大 minibatch 标准化；当 episode 很短时 std 估计会偏噪（有 `+1e-8` 兜底，不会除零）。
- **被后续版本保留**：v4 文档 §三 明确「保留 v2 的 advantage batch 标准化（独立的正确修复）」，v5 亦保留。这是 v2 中**唯一被公认为净正向**的算法改动。

#### 6.3.5 _masked_softmax（214-223）

标准 mask softmax：先减去合法 logits 的最大值（数值稳定），非法动作加 `1e5*(legal-1)` 压到极小。

## 10. 设计评价：优点 / 风险 / 可改进点

### 10.1 优点

1. **改动面极小（只 2 个文件），可归因性强**。相比大改结构，这种「只动奖励 + 一行 loss」的方式便于在集群上快速验证。
2. **advantage batch 标准化是教科书级正确修复**（§6.3.4）。恰好对症 v1「三头 value 尺度不统一 → policy 抖动」的症状，且不触碰 value 学习目标。
3. **buff 换通道有扎实的领域直觉**：加速 buff（一步两格、维持 50 步）本质是生存/机动资源，放进 survive 通道比 treasure 通道更合理；且提高强度以对抗「遇到概率低」的稀疏性。
4. **机会成本利用了「上一步」时序对齐**（先存后更新，§6.2.6），实现上严谨，没有 off-by-one。
5. **工程表述规范**：改动处均有中英双语注释、`py_compile` 通过，v1 目录完整保留作为基线。

### 10.2 风险与不足

1. **核心前提被证伪（最大风险）**：整批「穿梭冷启动」改动建立在**误读监控口径**之上。监控总览「闪现」图是 **flash_count 每帧速率**（≈3.7 次/局摊到 1000 帧 → 曲线贴 0），而模型评估页「技能使用次数」是**每局累计**。据前者判「穿梭从不使用」是误判；实测 v1/v2 都在 **CD 一好就用穿梭**（≈1.1 次/百步，已到使用上限）。参见 §10.4 辩证评述。
2. **无对照组，效果无法单独归因**。v2 同时改了 6 处激励 + 1 处算法；评估只有总分 849.23 这一个点（还比 v1 的 927.99 低）。**既不能证明 adv 标准化有效，也不能证明冷启动激励无效**——从数据看，很可能是「冷启动激励轻微有害 + adv 标准化略微有益」在互相抵消。
3. **奖励项分散在两个通道**：穿梭成功奖励进 step 通道，机会成本进 survive 通道，而 policy 用的是「三头 advantage 平均」。这会让「穿梭激励」的净信号被平均稀释，**方向相反的两项可能互相抵消**。
4. **激励方向可能反噬**：若模型本就该「保留技能到 300 步双怪包夹」使用，则「危险就用技能」的机会成本会**鼓励过早浪费 CD**，与后期生存需求冲突——这正是 v4 修正的方向（v4 改为单怪阶段「保留技能」、双怪阶段「精准落点」）。
5. **buff 仅靠拾取奖励难以触发**：buff 随机刷新、遭遇概率低，奖励再高也只有在「恰好遇到」时才有信号（v4 因此补了「靠近引导」）。
6. **advantage 标准化粒度偏小**：`learn()` 的批量来自单个 episode，标准化近似「局内标准化」，std 估计较噪（短局尤甚）。严格说不是主流 PPO 的「大 minibatch 标准化」。
7. **未处理的已知问题**（v2 文档 §四 自列）：截断未 bootstrap V(s_T)、value 未归一化、学习率/熵未退火、PPO epochs=1 数据复用低。

### 10.3 可改进点（v2 文档路线图节选）

| 优先级 | 改进 | 预期收益 |
|---|---|---|
| 高 | 课程学习（先单怪练走位，缩短 CD 高密度练穿梭，再双怪/加速） | 直接解决技能时机学习 |
| 高 | 规则 bot + 行为克隆（BC）warm start | 给穿梭/buff 提供高质量初始样本，降方差 |
| 中 | 学习率线性退火 3e-4→3e-5；熵系数退火 | 缓解后期震荡 |
| 中 | value/return running-std 归一化 + 相对 clip | 让 value clip 真正生效 |
| 中 | 截断正确 bootstrap V(s_T) | 消除 1000 步截断的 value 偏置 |
| 低 | 主干接 GRU/LSTM（POMDP 记忆） | 怪物出视野后不「失忆」 |

### 10.4 辩证评述：冷启动激励「被证伪」这一课

**v2 的自我叙事**是：「监控显示穿梭几乎不用 → 一定是奖励太弱导致冷启动 → 提高奖励、加重惩罚、加机会成本」。这套因果链**在逻辑上自洽**（v2 文档甚至给出了「尝试穿梭期望收益 > 不用技能」的自洽推导），失败点在**前提观测**，而不在推导。

**关键教训是「指标口径」**：

- 同一个词「闪现/穿梭使用」在**监控总览**与**评估页**含义不同——前者是**速率（per-frame rate）**，后者是**每局累计（per-episode count）**。
- 用速率图去判断「用不用」是典型的口径错配：3.64 次/局 摊到 1000 帧，曲线自然贴 0，但它**不是 0**。
- 正确做法是**交叉验证两个口径**，或直接看「是否达到理论上限」（CD=100 → 1000 步内最多约 10 次，实测 ~3.6 次，属正常使用）。

**结论**：

- 就 **v2 的冷启动激励而言**，方向错了。它把一个「既已发生的行为（在用穿梭）」误判成「缺失的行为」，于是对**已经饱和的行为再加激励**，只会强化滥用、并把「用技能」的时机进一步提前（与保留技能到双怪窗口的最优策略相悖）。评估总分低于 v1，与这一判断一致。
- 就 **advantage batch 标准化而言**，与冷启动激励**完全解耦**，是独立的、教科书级的正确修复，被 v4/v5 完整保留。
- 就**方法论而言**：v2 是「小改动、快速验证」精神的正面体现，但其**观测→归因**环节暴露了「单一监控口径不可信」的风险。v4 的复盘（区分速率/累计、并据此重写聚焦点）是这次迭代最有价值的产出——**否定一个改动，本身也是推进**。

> 一句话：**v2 = 一次建立在误读指标上的错误尝试（冷启动激励）+ 一次被证明正确的独立修复（advantage 标准化）**。前者被 v4 删除，后者被 v4/v5 继承。
